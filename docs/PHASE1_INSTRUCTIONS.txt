4. TASK B: SOL-13 EXPECTED-OUTPUT FORMULA AND HAND CALCULATION
--------------------------------------------------------------

Deliverables
  docs/expected_method.md                 formula, assumptions, peer method
  tests/fixtures/handcalc/handcalc.csv    10-20 real rows, worked by hand

B1. Physics baseline (write it down exactly)

    P_exp_w    = P_stc * (G / 1000) * (1 + gamma * (T - T_ref))
    P_stc      = site.json > module > stc_rating_w            (400)
    gamma      = site.json > module > temp_coefficients >
                 pmax_pct_per_c / 100                          (-0.0035)
    T_ref      = expected.reference_temp_c                     (25)
    G          = irradiance_used_wm2 (from quality: hub value, or row median)
    T          = temp_c (back-of-panel; state this assumption: cell temp is a
                 few C higher, so expected is slightly optimistic in sun)
    energy_kwh = power_w * interval_min / 60 / 1000            (interval = 15)

  Worked example to put in the doc:
    G = 800, T = 45  ->  400 * 0.8 * (1 - 0.0035 * 20) = 297.6 W = 0.0744 kWh
    V = 33.0, I = 8.6 -> 283.8 W = 0.07095 kWh
    deficit = 0.00345 kWh (4.6 %)

  Rules to state:
  - Skip intervals with G < expected.min_irradiance_wm2 (50). is_daylight is
    false for them.
  - Daily measured_kwh and expected_kwh are summed over the SAME intervals
    (usable and daylight). Otherwise gaps show up as fake losses.
  - loss_kwh = max(expected_kwh - measured_kwh, 0).

B2. Peer baseline (write it down)
  - Raw interval ratio = panel power / median power of its usable hub mates
    (itself excluded). With fewer than expected.peer.min_peers usable hub
    mates, use the usable panels in the same row.
  - "Healthy peer" means usable and daylight. It must NOT depend on
    classification (classification comes later, so that would be circular).
  - Normalize: peer_ratio = raw ratio / the panel's reference ratio. Reference
    ratio = median daily raw ratio over the panel's first
    expected.peer.reference_period_days days with usable data. If the data is
    shorter than that (the fixtures are), use all days.
  - State the limit: a whole hub or row that is down together has peer ratio
    ~1. Physics catches that case; peer ratio says WHO, physics says HOW MUCH.

B3. Hand calculation on real rows
  Pick 10-20 rows from input/mvp1/readings.csv:
  - 3-4 hubs across rows, e.g. H01, H06, H11 (avoid row 3 after January:
    sensor drift)
  - 2 clear days (weather ACSH < 30) and 1 cloudy day (ACSH > 80), in
    Sep-Oct 2025 (before snow)
  - G between 200 and 1000, and no sentinel, missing or out-of-range values
  Work each row in a spreadsheet, NOT with project code. Save the result as
  tests/fixtures/handcalc/handcalc.csv with these columns:
    timestamp_utc, hub_id, panel_id, irradiance_wm2, temp_c, voltage_v,
    current_a, power_w, energy_kwh, expected_power_w, expected_kwh, deficit_kwh
  In Phase 2 (SOL-22), test_expected.py loads it and asserts that expected.py
  is within expected.hand_calc_tolerance_pct (2 %). That test covers the
  brief's "within 2% of a hand calculation".

Done when: the doc and CSV are merged, and the numbers are checked twice.

7. TASK E: SOL-16 servicelog.py
-------------------------------

Contract: servicelog.analyze(service_log, events, windows, cfg) -> ServiceLog
          with .visits and .repeat_repairs (contracts.md section 8)

E1. repeat_repairs
  - Explode panel_list on visits with fault_found. Group by panel_id. Keep
    panels with at least servicelog.repeat_min_repairs repairs.
  - hub_id: from cfg.site["panels"]
  - ticket_ids and visit_dates: lists, sorted by date
  - root_cause: from the latest repair
  - permanent_fix: from a config map, not from code. Add:
        servicelog:
          permanent_fix:
            wiring: "Replace both connector halves with a matched pair from one maker"
            string_outage: "Replace fuse holder; inspect combiner for heat damage"
            hotspot: "Replace module under warranty"
  - On real data, expect P22 with 3 repairs (SR-1006, SR-1009, SR-1013),
    cause "cross mated connectors". SR-1003 (S2 fuse) is 1 repair on each of
    12 panels, so it is not a repeat.

E2. visits
  - matched_event_ids: events that overlap
    [visit_date - servicelog.match_window_days, visit_date] and share a panel
    with the visit ("ALL" matches every panel)
  - explained_by: label of the matched event with the largest kwh_lost, or ""
  - avoidable: not fault_found AND trigger != "scheduled" AND explained_by is
    in servicelog.avoidable_labels. Add avoidable_labels to the config.
    Recommended start: [weather] (see decision 5 in section 9).

E3. Tests: tests/test_servicelog.py on the fixture service log + fixture events
  - P05 is a repeat (after C2 adds SR-9003)
  - SR-9001 matches E0001, explained_by weather, avoidable
  - SR-9002 is not avoidable (a fault was found)
  - a scheduled visit is never avoidable
  Smoke run on input/mvp1 (prints only, not a test): P22 shows 3 repairs.

Done when: tests pass and the real-data smoke run lists P22.


8. TASK F: SOL-15 PDF LAYOUT
----------------------------

Change from the issue: render from tests/fixtures/results/ (Task C) instead of
a hard-coded dict. The fixture already holds fake numbers, and the code that
results is the start of SOL-26.

Library: matplotlib PdfPages (already installed). Letter portrait. One figure
per page, axis off, fig.text for headings, ax.table for tables.

F1. Shape of solarscope/report.py
  build_pages(results_dir) -> {window_name: [Page, ...6]}
      Reads the 5 files, filters by window, formats and rounds numbers. Does
      no analytics. Page = title + text lines + tables (plain lists).
  draw(pages, pdf_path)
      Only matplotlib. No numbers are computed here.
  render(results_dir) -> list[Path]
      Writes report_<window>.pdf for every window in summary.json["windows"].
      Window names and dates always come from the file.
  Splitting build from draw lets tests check the numbers on the Page objects,
  without parsing PDF text.

F2. The 6 pages (source in brackets)
  1 Summary          kWh actual/expected/lost, fault vs weather split, counts,
                     top 3 findings [summary.json window block]
  2 Fault or Weather kWh lost by label and cause, then the top N events by
                     kWh [events.csv]. "Every event" will not fit on one page
                     with a year of cloud days. Show the top N and the totals,
                     and say "full list: events.csv".
  3 Dispatch List    one line per dispatch_id (a string outage is 12 panels on
                     1 line), priority, cause, evidence, kWh [dispatch.csv]
  4 Repeat Repairs   [summary.json repeat_repairs]. Handle an empty list:
                     "No panel repaired more than once".
  5 Early Warnings   panel, rate %/month, first flag, projected 10 % date
                     [events.csv label early_warning]
  6 Data Quality     usable % per hub, excluded periods, rules used (from
     and Method      summary.json config), run ID, config hash, input checksums
                     [data_quality.csv, summary.json]
  Every table has a row cap (a module constant). Exactly 6 pages, always.

F3. Test: tests/test_report.py
  - render(copy of the fixture folder in tmp_path) writes 2 PDFs
  - each PDF has 6 pages. Count b"/Type /Page" occurrences that are not
    followed by "s"; matplotlib writes these uncompressed, so no new
    dependency is needed.
  - page 1 of 365d contains the fixture's kwh_lost_total, formatted

Done when: both PDFs open cleanly, have 6 pages each, and contain no raw
readings.


9. DECISIONS TO RECORD (answer in contracts.md or the config, not in chat)
--------------------------------------------------------------------------

1. A single missing hub irradiance value (not a whole excluded period): row
   median fallback or NaN? Agree with dtri. It changes is_usable and
   usable_pct.
2. Peer reference period = the first N days with usable data (section B2).
   Fine unless a panel is already faulty in its first 30 days.
3. Measured and expected summed over the same intervals (section B1).
   Recommended: yes.
4. Repeat repairs per window. The 180d window contains only P22's 3rd repair.
   Recommended: show a panel if ANY of its repairs falls in the window, and
   list its full history. Otherwise the 180-day report hides the worst repeat
   problem.
5. Which no-fault visits count as "truck rolls avoided"? Scheduled visits:
   never. Weather: yes. Hub offline (SR-1004 needed a breaker reset on site,
   SR-1014 came back by itself) and the hub sensor visit (SR-1011): judgment.
   Start with avoidable_labels: [weather] and widen it only with a reason.
6. Report page 2 shows the top N events plus totals, not every event (section
   F2).
7. Fixtures: one tests/fixtures/results/ folder instead of 4 per-owner folders
   (section 5).
